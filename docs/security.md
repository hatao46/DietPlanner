# セキュリティ設計書

## 1. 概要

本書は、Diet Plannerにおけるセキュリティ対策の方針を定義する。個人情報(体重・食事・運動記録等の健康関連データ)を扱うため、認証・認可・通信保護・入力値検証を中心に対策する。方針の一覧は[README.md](../README.md)「11. セキュリティ方針」および[非機能要件定義書](./requirements/non-functional-requirements.md)「6. セキュリティ」に基づく。本書中の「SC-05」「DT-02」等のIDは、非機能要件定義書の要件IDを指す。

## 2. 認証・認可

- 認証はLaravel標準の認証機能(パスワードハッシュ化、セッション管理)を利用する
- パスワードは平文で保存せず、Laravelのハッシュ化機能(bcrypt/argon2)で保存する
- 認可はLaravelのPolicyを用い、ユーザーは自身が作成した体重・食事・運動記録、プロフィールのみ閲覧・編集・削除できるようにする
- 他ユーザーのデータへのアクセス試行(URL直接指定等)は403として拒否する(SC-03、SC-04)
- 未認証ユーザーは保護画面へアクセスできないようにする(SC-02)
- ログイン試行が一定回数連続で失敗した場合は、試行を一時的に制限する(SC-05)
- セッションCookieにはSecure、HttpOnly等の安全属性を設定する(SC-20)

## 3. 通信の保護(TLS等)

- 本番・ステージング環境は、AWS Certificate Managerで発行したTLS証明書を用い、Application Load BalancerでHTTPS終端を行う
- 本番環境はHTTPSのみで公開し、HTTP接続はHTTPSへリダイレクトする
- ローカル環境はHTTPでの開発を許容する

## 4. データ保護(暗号化・個人情報)

- 体重・食事・運動記録は個人の健康情報に準じるものとして扱い、第三者への公開機能(SNS連携等)はMVP対象外とする(README.md「4. MVPの対象外」参照)
- 収集する個人情報はメールアドレスのみとし、氏名・住所・電話番号は収集しない(DT-01、DT-02)
- メールアドレスは認証・パスワード再設定の目的以外に使用しない(DT-03)
- 本番データをローカル環境へコピーしない。ステージング環境ではテストデータを使用する(DT-05、DT-06)
- 退会時のデータ削除方針は実装前に決定する(DT-04)
- RDSのデータは保管時暗号化(暗号化オプション)の利用を検討する
- バックアップ(スナップショット)についても暗号化を維持する

## 5. 入力値検証・脆弱性対策

- SQLインジェクション: LaravelのEloquent ORM/クエリビルダを使用し、生SQLの文字列結合を避ける(SC-17)
- XSS: Vue 3のテンプレートエンジンによる自動エスケープを基本とし、`v-html`等の使用は原則禁止する。Laravel側でも出力エスケープを徹底する(SC-18)
- CSRF: LaravelのCSRFトークン機構(VerifyCsrfTokenミドルウェア)を有効にする(SC-16)
- 入力値バリデーション: すべての登録・更新処理でサーバーサイドバリデーションを行う(SC-19)
- エラー画面: 本番環境ではデバッグ表示を無効化し、スタックトレース等の内部情報を表示しない(SC-21)

## 6. シークレット管理

- AWSルートユーザーにMFAを設定し、日常の作業ではルートユーザーを使用しない(README.md「11. セキュリティ方針」参照)
- `.env`ファイルはGitへコミットしない(SC-11)。DBパスワード等をソースコードへ記載しない(SC-12)
- AWS上の秘密情報(DB接続情報、APIキー等)はAWS Systems Manager Parameter Store(必要に応じてSecrets Manager)で管理する
- AWSアクセスキーはGitHubリポジトリへ保存せず、GitHub ActionsとAWSはOIDCで連携する
- EC2へのアクセスはAWS Systems Manager Session Managerを利用し、SSHポートはインターネットへ公開しない

## 7. ログ・監査

- アプリケーションログ・アクセスログはCloudWatchへ送信する
- ログにパスワード、セッショントークン、その他の秘密情報を出力しない
- 認証失敗、権限エラー等のセキュリティ関連イベントは記録し、異常な連続失敗を検知できるようにする(詳細は[monitoring.md](./monitoring.md)参照)

## 8. 脆弱性管理・アップデート方針

- PHP・Laravel・npm依存パッケージのバージョンは定期的に確認し、既知の脆弱性が報告された場合は速やかにアップデートする
- `composer audit`および`npm audit`をCIまたは定期作業として実行し、依存パッケージの既知の脆弱性を検査する(SC-22)
- GitHub Actionsによる静的解析(LarastanまたはPHPStan)、ESLintをCIに組み込み、コード品質・既知の危険なパターンを検出する
- Dockerベースイメージも定期的に最新化し、既知の脆弱性を含むイメージの利用を避ける
