# 非機能要件定義書

## 1. 文書の目的

本書は、Diet Plannerの可用性、性能、セキュリティ、バックアップ、ログ、監視、費用など、機能要件以外に求める品質要件を定義するものです。

本プロジェクトは個人開発および学習を目的としているため、商用サービスと同水準の可用性は要求しません。

一方で、AWS上で公開するWebサービスとして、障害検知、バックアップ、復旧、セキュリティ、費用管理の基本を実践できる構成を目指します。

---

## 2. 対象環境

| 環境         | 用途          | 非機能要件の適用 |
| ---------- | ----------- | -------- |
| Local      | 開発・デバッグ     | 一部適用     |
| Staging    | 結合試験・デプロイ確認 | 原則適用     |
| Production | 一般公開・実利用    | すべて適用    |

---

## 3. 要件レベル

各要件を次の3段階に分類します。

| レベル | 意味              |
| --- | --------------- |
| 必須  | 本番公開までに満たす      |
| 目標  | 可能な範囲で満たす       |
| 将来  | 初期リリース後に対応を検討する |

## 4. 可用性

### 4.1 基本方針

個人開発サービスであるため、24時間365日の完全な無停止運用は要求しません。

障害が発生した場合に検知でき、一定時間内に復旧できることを重視します。

### 4.2 要件

| ID    | 要件                  |        目標値 | レベル | 確認方法                              |
| ----- | ------------------- | ---------: | --- | --------------------------------- |
| AV-01 | 本番環境を常時アクセス可能な状態とする | 月間稼働率99%以上 | 目標  | CloudWatch、外形監視                   |
| AV-02 | 計画停止時は事前に影響を把握する    |     作業前に確認 | 必須  | リリース手順                            |
| AV-03 | アプリケーション異常を検知する     |       5分以内 | 必須  | ALB Health Check、CloudWatch Alarm |
| AV-04 | 障害発生後にサービスを復旧する     |     24時間以内 | 必須  | 復旧試験                              |
| AV-05 | 直前バージョンへ戻せること       |   30分以内を目標 | 必須  | ロールバック試験                          |

### 4.3 初期リリースで許容する事項

* EC2はステージング、本番ともに各1台構成とする
* EC2の冗長化は行わない
* RDS Multi-AZは初期リリースでは使用しない
* デプロイ時に短時間の停止が発生する可能性を許容する
* AWSリージョン障害への対応は対象外とする

## 5. 性能

### 5.1 想定利用規模

| 項目            |     想定値 |
| ------------- | ------: |
| 登録ユーザー数       |   10人以下 |
| 同時利用者数        |    3人以下 |
| 1ユーザー当たりの体重記録 |    1日1件 |
| 1ユーザー当たりの食事記録 | 1日10件以下 |
| 1ユーザー当たりの運動記録 |  1日5件以下 |

### 5.2 要件

| ID    | 要件             |     目標値 | レベル | 確認方法                  |
| ----- | -------------- | ------: | --- | --------------------- |
| PF-01 | 通常画面の初期表示      |    3秒以内 | 目標  | Playwright、ブラウザ開発者ツール |
| PF-02 | 登録・更新処理        |    2秒以内 | 目標  | E2Eテスト、アプリログ          |
| PF-03 | ダッシュボード表示      |    3秒以内 | 目標  | Playwright            |
| PF-04 | Health Check応答 |    1秒以内 | 必須  | curl、ALB Health Check |
| PF-05 | 通常利用時のCPU使用率   | 平均70%未満 | 目標  | CloudWatch            |
| PF-06 | ディスク使用率        |   80%未満 | 必須  | CloudWatch Agent      |

### 5.3 性能試験方針

初期リリースでは大規模負荷試験は実施しません。

以下を最低限確認します。

* 主要画面の応答時間
* 連続した登録処理でエラーが発生しないこと
* 複数ブラウザから同時操作できること
* DBクエリが過剰に発行されていないこと
* ダッシュボード表示でN+1問題が発生していないこと

## 7. バックアップ・復旧

### 7.1 バックアップ要件

| ID    | 対象        | 要件                    |       保存期間 | レベル |
| ----- | --------- | --------------------- | ---------: | --- |
| BK-01 | RDS       | 自動バックアップを取得する         |        7日間 | 必須  |
| BK-02 | RDS       | 本番変更前に手動スナップショットを取得する |        必要時 | 必須  |
| BK-03 | S3        | 誤削除対策を行う              | バージョニングを検討 | 目標  |
| BK-04 | Terraform | GitHubで履歴管理する         |        無期限 | 必須  |
| BK-05 | アプリケーション  | GitHubでソースコードを管理する    |        無期限 | 必須  |

### 7.2 復旧目標

| 用語  | 目標               |
| --- | ---------------- |
| RTO | 24時間以内           |
| RPO | 最大24時間分のデータ損失を許容 |

RTOは障害発生からサービス復旧までの目標時間です。

RPOは障害発生時に許容するデータ損失期間です。

### 7.3 復元試験

以下を本番公開前に1回実施します。

1. RDSのスナップショットを取得する
2. スナップショットから別のRDSを作成する
3. ステージングアプリケーションから接続する
4. ユーザーおよび記録データを確認する
5. 復旧に要した時間を記録する
6. 問題点を`docs/backup-restore.md`へ記録する

## 10. 費用上限

### 10.1 月額予算

| 区分    |             目標 |
| ----- | -------------: |
| 通常月額  |       5,000円以内 |
| 許容上限  |       8,000円以内 |
| 上限超過時 | 構成見直しまたは一部環境停止 |

AWS料金は為替、利用時間、通信量、構成変更によって変動するため、固定料金ではなく予算上限として管理します。

### 10.2 費用管理要件

| ID    | 要件                           | レベル |
| ----- | ---------------------------- | --- |
| CO-01 | AWS Budgetsを設定する             | 必須  |
| CO-02 | 月額予算の50%、80%、100%で通知する       | 必須  |
| CO-03 | 不要なEC2、EBS、Elastic IPを定期確認する | 必須  |
| CO-04 | ステージング環境の停止可能性を検討する          | 目標  |
| CO-05 | CloudWatch Logsの保存期間を無期限にしない | 必須  |
| CO-06 | ECRの古いイメージをライフサイクルポリシーで削除する  | 必須  |
| CO-07 | 毎月の費用を記録する                   | 必須  |

### 10.3 費用超過時の対応順序

1. 不要なAWSリソースを削除する
2. CloudWatch Logsの保存期間を見直す
3. 古いECRイメージを削除する
4. ステージングEC2の常時起動を見直す
5. EC2およびRDSのインスタンスサイズを見直す
6. ALBを使用しない簡易構成への変更を検討する
