# バックアップ・リストア設計書

## 1. 概要

本書は、Diet Plannerにおけるデータ保護のためのバックアップ・リストア方針を定義する。対象は主にAmazon RDS(PostgreSQL)上のユーザーデータである。要件は[非機能要件定義書](./requirements/non-functional-requirements.md)「7. バックアップ・復旧」に基づく。本書中の「BK-01」等のIDは、同書の要件IDを指す。

## 2. バックアップ対象

- Amazon RDS PostgreSQL(ユーザー、プロフィール、体重・食事・運動記録等すべてのアプリケーションデータ)
- Terraformコード・アプリケーションコード(GitHubリポジトリで履歴管理されるため、別途のバックアップは不要とする。BK-04、BK-05)
- Dockerイメージ(Amazon ECRで保持されるため、別途のバックアップは不要とする)
- Amazon S3(MVP時点では未使用。利用開始時はバージョニングによる誤削除対策を検討する。BK-03、TODO-04)

## 3. バックアップ方式・スケジュール

| 対象 | 方式 | 頻度 | 保持期間 |
|------|------|------|----------|
| RDS PostgreSQL(本番) | RDS自動バックアップ(スナップショット) | 日次(自動) | 7日間(BK-01) |
| RDS PostgreSQL(本番) | 手動スナップショット(BK-02) | 本番DBに影響する変更・マイグレーション作業の前 | 作業の完了確認後に削除 |
| RDS PostgreSQL(ステージング) | RDS自動バックアップ(スナップショット) | 日次(自動) | 1〜3日間 |

## 4. リストア手順

1. AWSマネジメントコンソールまたはAWS CLIから、対象環境のRDSインスタンスの自動バックアップ一覧を確認する
2. 復元したい時点のスナップショットを選択し、新しいRDSインスタンスとして復元する
3. アプリケーション(EC2)の接続先を復元後のRDSエンドポイントへ切り替える(Parameter Storeの値を更新)
4. アプリケーションを再起動し、Health Checkで正常性を確認する
5. 復元元の旧インスタンスは、動作確認後に削除する

詳細な障害対応手順は[runbook.md](./runbook.md)を参照する。

## 5. 目標値

- RPO(目標復旧時点): 最大24時間分のデータ損失を許容する(RDS自動バックアップの日次取得を前提とする。非機能要件定義書 7.2)
- RTO(目標復旧時間): 24時間以内(AV-04、非機能要件定義書 7.2)

なお、アプリケーション不具合時の直前Dockerイメージへのロールバックは30分以内を目標とする(AV-05)。これはDBリストアとは別の手順であり、[runbook.md](./runbook.md)「3. デプロイ手順」を参照する。

## 6. リストア訓練・検証

- 本番公開前に最低1回、リストア手順を検証する([README.md](../README.md)「12. 公開条件」の「バックアップから復元できることを確認している」に対応)
- 検証は非機能要件定義書「7.3 復元試験」の手順に従う: スナップショット取得 → 別RDSインスタンス作成 → ステージングアプリケーションから接続 → ユーザー・記録データの確認 → 所要時間の記録
- 検証で判明した問題点・所要時間は本書へ追記する

## 7. 障害シナリオ別対応

| シナリオ | 対応方針 |
|----------|----------|
| 誤ったデータ削除・更新 | 直近のスナップショットから復元し、必要なデータのみ移行する |
| RDSインスタンス障害 | 自動バックアップから新規インスタンスを復元し、接続先を切り替える |
| マイグレーション失敗によるDB破損 | 作業前に取得した手動スナップショット(BK-02)から復元する |
| リージョン全体障害 | MVPでは他リージョンへの切り替えは対象外とする(非機能要件定義書 4.3)。復旧まで待機する |
