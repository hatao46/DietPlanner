# 運用手順書(Runbook)

## 1. 概要

本書は、Diet Plannerの定常運用、デプロイ、障害対応の手順を定義する。対象環境はローカル・ステージング・本番の3環境である([README.md](../README.md)「7. 環境構成」参照)。本書中の「AV-04」「BK-02」等のIDは、[非機能要件定義書](./requirements/non-functional-requirements.md)の要件IDを指す。

## 2. 定常運用

### 2.1 起動・停止手順

- ローカル環境: `docker compose up -d --build`で起動、`docker compose down`で停止する(README.md「15. ローカル環境の起動方法」参照)
- ステージング・本番環境: EC2インスタンス上でDockerコンテナとして常時稼働させる。インスタンスの起動・停止はAWSマネジメントコンソールまたはAWS CLI、もしくはTerraformで管理する

### 2.2 日次・週次・月次作業

| 頻度 | 作業内容 |
|------|----------|
| 日次 | CloudWatchダッシュボード・アラート状況の確認(必要に応じて) |
| 週次 | 依存パッケージの脆弱性情報の確認(`composer audit`、`npm audit`) |
| 月次 | AWS費用の記録とAWS Budgets通知状況の確認(CO-07) |
| 月次 | 不要なEC2、EBS、Elastic IP等のリソース確認・削除(CO-03) |
| 月次 | RDSバックアップからのリストア手順の確認(本番公開後は定期的に実施を検討) |

## 3. デプロイ手順

README.md「7. 環境構成」「9. CI/CD方針」に基づき、以下の流れでデプロイする。

1. `main`ブランチへマージすると、GitHub Actionsが本番用Dockerイメージをビルドする
2. GitコミットSHAをタグとして付与し、Amazon ECRへpushする
3. ステージングEC2へ自動デプロイし、DBマイグレーションとHealth Checkを実行する
4. ステージング環境でE2Eテストを実行する
5. テスト成功後、GitHub Actions上で本番デプロイを承認する
6. 本番のDBに影響する変更(マイグレーション等)を含む場合は、事前にRDSの手動スナップショットを取得する(BK-02)
7. ステージングで確認済みのDockerイメージを本番へデプロイし、DBマイグレーションとHealth Checkを実行する
8. 本番デプロイに失敗した場合は、直前のDockerイメージへロールバックする(30分以内を目標とする。AV-05)

## 4. 障害対応

### 4.1 一次対応フロー

1. CloudWatchアラートまたはHealth Check失敗を検知する
2. 対象環境(ステージング/本番)、影響範囲(全体障害/一部機能)を確認する
3. アプリケーションログ・インフラログ(CloudWatch Logs)を確認し、原因を特定する
4. 直前のデプロイが原因と判断できる場合は、直前のDockerイメージへロールバックする(本書「3. デプロイ手順」参照)
5. データ破損等が疑われる場合は、[backup-restore.md](./backup-restore.md)に従いリストアを検討する
6. 復旧後、原因と対応内容を記録する

復旧目標は障害発生から24時間以内とする(AV-04)。直前バージョンへのロールバックは30分以内を目標とする(AV-05)。

### 4.2 エスカレーション基準

個人開発プロジェクトのため、エスカレーション先は開発者本人のみとする。将来的にチーム体制になった場合は、本項を見直す。

## 5. よくある障害と対処法

| 事象 | 原因 | 対処 |
|------|------|------|
| Health Checkが失敗する | アプリケーションコンテナの起動失敗、DB接続不可 | EC2上のコンテナログを確認し、環境変数・DB接続設定を確認する |
| デプロイ後に5xxエラーが増加する | マイグレーション未実行、設定値の不整合 | 直前のDockerイメージへロールバックし、原因調査後に再デプロイする |
| RDSへ接続できない | セキュリティグループ設定、RDS障害 | セキュリティグループ・RDSステータスを確認する。復旧しない場合は[backup-restore.md](./backup-restore.md)のリストア手順を検討する |
| ステージング環境のE2Eテストが失敗する | 実装不備、テストデータ不整合 | テスト結果を確認し、原因を修正したうえで再度`main`へマージする |

## 6. 連絡先・体制

本プロジェクトは個人学習用のため、運用担当は開発者本人(1名)とする。チーム体制での運用は現時点では想定しない。
